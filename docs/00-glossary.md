## AI와 개발 방법

| 말 | 한 줄 뜻 |
|---|---|
| 바이브 코딩 | 코드를 확인하지 않고 AI에게 맡기는 방식 |
| 책임감 있는 AI 지원 개발 | AI가 쓰되 테스트와 변경 내용을 사람이 확인하는 방식 |
| 프롬프트 | AI에게 보내는 말 |
| agy | 터미널에서 쓰는 AI 에이전트(Antigravity CLI). 프로젝트 폴더 터미널에서 `agy`를 입력해 켭니다 |
| 컨텍스트 창 | AI가 한 번에 볼 수 있는 작업 책상. 크기에 한계가 있습니다 |
| 컨텍스트 오염 | 대화가 길어져 옛 결정, 실패한 코드, 관계없는 이야기가 섞여 답이 흔들리는 일. 새 채팅(+ 버튼)으로 풉니다 |
| AGENTS.md | AI가 일을 시작할 때마다 읽는 프로젝트 규칙. AI에게 하는 '부탁'입니다 |
| 스킬(SKILL.md) | 특정 작업의 레시피. `.agents/skills/<이름>/SKILL.md`에 두고, 이름과 설명을 보고 필요할 때만 본문을 불러옵니다 |
| frontmatter | SKILL.md 맨 위 `---` 사이의 설정 부분(name, description 등) |
| MCP (Model Context Protocol) | AI에 바깥 도구를 꽂는 표준 연결. 오늘은 Context7(라이브러리 최신 문서 찾기)을 두 방식으로 붙입니다 |
| Node.js / npx | `npx`는 Node.js에 들어 있는 실행 도구. npm 방식 MCP 서버를 내 PC에서 실행할 때 씁니다 |
| 하네스 | AI를 감싸는 검증·재시도·승인 장치. 오늘은 테스트와 수정 범위 확인입니다 |
| 확률적 / 결정적 | 같은 입력이라도 결과가 달라질 수 있음(AI 모델) / 같은 입력이면 늘 같은 결과(규칙, 예시표로 고정) |
| 프리모템 | 보내기 전 점검. "이 프롬프트가 의도대로 안 될 경우의 수는?"을 먼저 묻는 습관 |
| 포스트모템 | 끝난 뒤 기록. 다시 보낸 프롬프트와 처음에 넣었어야 할 말을 적습니다 |
| 이해 부채 | AI가 쓴 코드를 이해하지 못한 채 쌓아 두어 나중에 고치지도 설명하지도 못하게 되는 빚 |
| 계획자 · 생성자 · 평가자 | 사람은 계획(명세), AI는 생성(테스트 행·코드), 테스트는 평가(통과·실패 판정) |
| Launch · Observe · Evaluate · Improve | 출시 → 관찰 → 평가 → 개선. 출시한 뒤에도 도는 고리 |

## 명세와 테스트

| 말 | 한 줄 뜻 |
|---|---|
| 명세(서) | 사람과 AI가 맺는 약속을 적은 문서. 오늘은 `SPEC.md`(규칙)와 `SPEC_COUPON.md`(쿠폰 규칙, 세션 4에서 내가 씁니다) |
| SDD | 명세 주도 개발. 집을 짓기 전에 설계도를 그리듯, 코드를 만들기 전에 명세를 먼저 쓰는 방법. 쉬운 설명은 [개념 노트](00-concepts.md) 11절 |
| API 명세 | 주소, 요청, 응답, 규칙, 오류 번호만 적은 약속. 파일을 어떻게 나눌지는 적지 않습니다. 세션 4에서는 지금 서비스의 쿠폰 API를 보고 직접 씁니다 |
| 명세의 세 기둥 | 맥락(왜·무엇을 받고 돌려주나), 통제(무엇을 하고 무엇은 안 하나), 정확성(완료를 어떻게 증명하나) |
| 예시표 | "이 입력이면 이 결과"를 줄마다 적은 표. 한 줄이 테스트 한 줄이 됩니다 |
| 수용 기준 | "이 조건을 통과하면 합격"이라는 기준. 예시표의 한 줄이 곧 수용 기준입니다 |
| EARS | 수용 기준을 "~하면 ~한다"(WHEN 조건 THE SYSTEM SHALL 동작)로 쓰는 형식 |
| 경계값 | 규칙이 바뀌는 딱 그 지점의 값(예: 점수 0.5, 글자 수 30자). 예시표에 꼭 넣습니다 |
| 테스트 | 코드가 예시표대로 동작하는지 자동으로 확인하는 프로그램 |
| pytest | 파이썬 테스트를 돌려 PASSED / FAILED로 보여 주는 도구. 사용법은 [pytest 소개](02-pytest.md) |
| assert | 테스트 안에서 "이래야 한다"를 적는 한 줄. 틀리면 AssertionError가 납니다 |
| TDD | 테스트 주도 개발. 코드를 만들기 전에 테스트를 먼저 쓰고, 테스트가 통과하도록 코드를 만드는 방법. Red → Green → Refactor 순서로 돕니다 |
| Red | 테스트가 FAILED(실패)인 상태. 코드를 만들기 전에는 정상입니다 |
| Green | 테스트가 모두 PASSED(통과)인 상태 |
| Refactor (리팩터링) | 동작은 그대로 두고 코드를 읽기 쉽게 정리하는 일. 테스트가 지켜 주므로 안심하고 할 수 있습니다 |
| 자가 치유 | AI가 테스트를 돌리고, 실패하면 원인을 찾아 고치고, 다시 돌리는 일을 스스로 반복하는 것. 테스트가 있어야 가능합니다 |
| 계약 테스트 | HTTP 요청을 보내고 응답(번호, 내용)만 확인하는 테스트. 코드를 어떻게 나눴는지는 보지 않습니다 |
| PASSED / FAILED | `pytest -v`가 한 줄마다 보여 주는 통과 / 실패 |
| 수정 범위 확인 | agy의 `/diff`(Copilot은 소스 제어 창)로 AI가 고치라고 한 파일만 고쳤는지, `tests/`나 `SPEC.md`(세션 4는 `SPEC_COUPON.md`)를 건드리지 않았는지 보는 일 |
| 하드코딩 | 규칙을 따르지 않고 테스트의 값을 코드에 그대로 박아 넣는 꼼수(오늘은 금지) |
| 멱등성 | 같은 요청을 몇 번 해도 결과가 같은 성질. 같은 리뷰는 늘 같은 쿠폰 코드 |

## 환경

| 말 | 한 줄 뜻 |
|---|---|
| 터미널 | 글자로 컴퓨터에 일을 시키는 창. 오늘은 VS Code 안의 터미널을 씁니다 |
| 가상환경(venv) | 이 프로젝트만 쓰는 파이썬 상자. 켜지면 터미널 앞에 `(.venv)`가 보입니다 |
| pip | 파이썬 패키지(남이 만든 도구 모음)를 내려받는 명령. `pip install -r requirements.txt` |
| 인터프리터 | 파이썬 코드를 실제로 실행하는 프로그램. VS Code에서 `.venv`가 붙은 것을 고릅니다 |
| 템플릿 | 새 저장소를 만들 때 복사해 쓰는 원본 저장소. 강사가 준비해 두었습니다 |
| 브랜치 | 저장소 안의 한 갈래. 오늘은 `cp1-setup`, `cp2-spec` 같은 완성본 갈래로 따라잡습니다 |
| FastAPI | 이 프로젝트의 API를 만든 파이썬 도구(코드는 읽지 않습니다) |
| API | 프로그램끼리 주고받는 창구. 화면이 API에 요청을 보내고 결과를 받습니다 |
| uvicorn | FastAPI 서비스를 내 PC에서 실행해 주는 서버 프로그램(`uvicorn app.main:app --reload`) |
| localhost | "내 컴퓨터 자신"을 가리키는 주소. `http://localhost:8000`은 내 PC에서 켠 서비스 화면입니다 |
| 환경 변수 | 코드 밖에서 프로그램에 넣어 주는 값. 비밀값은 코드에 쓰지 않고 `.env` 같은 코드 밖의 파일에 둡니다 |
| Hugging Face | AI 모델을 올려 두고 내려받는 사이트. 오늘의 감정 분석 모델이 여기 있습니다 |

## 응답 번호 (HTTP 상태 코드)

서버가 돌려주는 결과 번호입니다.

| 번호 | 한 줄 뜻 |
|---|---|
| 200 | 성공 (분석 결과가 나옴) |
| 422 | 입력이 규칙에 맞지 않음 (예: 빈 글, 500자 초과, 별점 6) |
| 405 | 이 주소는 이 방식(POST)을 받지 않음 (쿠폰 API를 만들기 전에 보입니다) |
| 501 | 아직 만들지 않은 기능 (오늘 처음 화면에 보이는 숫자) |
| 503 | AI 부품이 응답하지 못함 (모델을 못 불러왔을 때 등) |
